## Movement, Combat and Physics

- `Examples/Pong/Scripts/Ball.cs`: `OnStartServer` and `OnCollisionEnter2D` resolve the ball on the server. `Examples/Pong/Scripts/Player.cs::FixedUpdate` gates paddle input with `isLocalPlayer`. `Examples/Pong/Scripts/NetworkManagerPong.cs::OnServerAddPlayer/OnServerDisconnect` illustrates association/spawn/cleanup, not a complete reconnect or slot-allocation policy.
- `Examples/TopDownShooter/Scripts/PlayerTopDown.cs::OnStartLocalPlayer/Update/CmdShoot` separates local input/UI and network state. **`CmdShoot(GameObject target)` trusts a client target and lacks full server range, LOS and fire-rate checks.** Preserve the target game's actual combat/AI; use server rule checks rather than copying this damage path, tag/name matching or unlimited shooting.
- `Examples/PlayerTest/PlayerTestNetMan.cs` and `Examples/PlayerTest/{CharacterController,Rigidbody,Tank}/` provide component/configuration comparisons, including Reliable, Unreliable and Hybrid prefabs. Follow referenced scripts and inheritance; the manager's many empty callbacks are not a complete bootstrap to copy.
- `Components/NetworkRigidbody/NetworkRigidbodyReliable.cs::FixedUpdate/OnStopServer/OnStopClient` **inherits `NetworkTransformReliable`** here. A second transform synchronizer on the same target creates competing writes. Inspect `target`, direction, interval, rigidbody mode and actual controller/AI writers in saved assets. `Components/NetworkTransform/NetworkTransformBase.cs::Reset` chooses `ClientToServer`, despite NetworkBehaviour's general server-to-client default. Check ownership transfer as well as session stop: restoring a kinematic flag on stop alone does not prove the new writer simulates correctly.

## Room, Selection and Replacement

- `Components/NetworkRoomManager.cs::OnRoomServerCreateRoomPlayer/OnRoomServerCreateGamePlayer/OnRoomServerSceneLoadedForPlayer/OnRoomServerPlayersReady`: prefer `OnRoom*` extension points so base room orchestration survives. `OnRoomServerSceneLoadedForPlayer` transfers approved room state before gameplay-player replacement. Decide when selection locks, readiness resets, late join is allowed, and transition failure recovers.
- `Examples/CharacterSelection/Scripts/NetworkManagerCharacterSelection.cs::OnCreateCharacter/OnReplaceCharacterMessage` demonstrates messages and `AddPlayerForConnection/ReplacePlayerForConnection`. Creation partially validates selection; replacement directly indexes the prefab array. Validate **every** entry point: bounds, registered allowed prefab, finite colour/data, bounded name, connection identity, session phase, duplicate requests and game-specific unlocks. Initialize state before spawn/replacement where possible. Check the installed overload/options and old-object cleanup; a fixed delayed destroy is not a universal completion guarantee.
- `Examples/TankTheftAuto/Scripts/TankAuthority.cs::CmdTakeControl/CmdReleaseControl` demonstrates injected Command sender and player replacement. Add server proximity, vacancy and eligibility checks. Its temporary `conn.authenticationData` stores the original player: use the project's session/character association instead when authentication data already holds login/account context. Preserve that context through release, disconnect and replacement failure.
- `Examples/CouchCoop/Scripts/CouchPlayerManager.cs::CmdAddPlayer` uses `NetworkServer.Spawn(playerObj, connectionToClient)` for extra owned objects. This does not create several primary `conn.identity` associations; choose input routing and cleanup for each controlled object explicitly.

## Additive Loading and Instance Isolation

- `Examples/AdditiveLevels/Scripts/AdditiveLevelsNetworkManager.cs::OnClientChangeScene/LoadAdditive/OnServerReady/AddPlayerDelayed` and `Portal.cs::SendPlayerToNewScene` coordinate scene messages, loading flags, Host avoiding duplicate loads, and remove/move/re-add of a player. Use bounded readiness/acknowledgement tied to the current transition; a fade delay or end-of-frame wait does not prove the remote client finished loading. Cancel pending joins/transfers on disconnect or shutdown.
- `Examples/MultipleAdditiveScenes/Scripts/MultiSceneNetManager.cs::ServerLoadSubScenes/OnServerAddPlayerDelayed/OnStopServer` loads repeated instances with `LocalPhysicsMode.Physics3D` and moves a player before association. Validate instance count/availability before indexing, associate pending joins with valid connections, retain actual loaded Scene handles, and coordinate stop/unload with restart. The sample's scene-index assumptions need adaptation when other scenes are already loaded.
- `Components/InterestManagement/Scene/SceneInterestManagement.cs::OnCheckObserver/OnRebuildObservers` uses actual `Scene` values because names can repeat. `Components/InterestManagement/PhysicsSimulator/PhysicsSimulator.cs::Awake/FixedUpdate` explicitly simulates server local physics scenes. Use the appropriate PhysicsScene/PhysicsScene2D for queries and spawning; global raycasts can hit the wrong world. The MultipleAdditiveScenes README still mentions `NetworkSceneChecker`; inspect real components.
- `Examples/MultipleAdditiveScenes/Scripts/Spawner.cs::SpawnReward` moves rewards into their scene before spawning. Ensure dropped items, projectiles, AI and pool reuse inherit the correct instance. Verify message routing, business interaction and physics isolation separately; observer filtering alone proves none of the other two.

## Match Membership

- `Examples/MultipleMatches/Scripts/CanvasController.cs::OnServerMatchMessage/OnServerJoinMatch/OnServerStartMatch/OnServerDisconnect` illustrates lobby state/messages. `Components/InterestManagement/Match/NetworkMatch.cs::matchId` is server-set; `MatchInterestManagement.cs::OnCheckObserver/OnRebuildObservers` filters nonempty match IDs and rebuilds observers.
- Validate actual authenticated connection, current membership, capacity, readiness, allowed transitions and supplied match IDs in every message/Command. `Examples/MultipleMatches/Scripts/MatchController.cs::CmdMakePlay/CmdRequestExitGame` is a starting point for sender checks, not automatic permission on every handler. Client invisibility is insufficient: try known foreign object IDs, forged match messages and cross-world physics queries on the server.

## Equipment, Contention and Pooling

- `Examples/PickupsDropsChilds/Scripts/PickupsDropsChilds.cs::OnChangeEquippedItemConfig/OnChangeEquipment/ChangeEquipment/CmdDropItem` reconstructs local child visuals from recoverable equipment/configuration state; drops become separate spawned objects. Preserve declaration/order dependencies or use a coherent snapshot and idempotent presentation. Struct SyncVars use copy/mutate/reassign. Do not duplicate a gameplay mutation through both a hook and an RPC.
- **`CmdPickupItem` is a teaching path, not a validated transaction.** It lacks complete null/spawn/type, eligibility, distance/LOS, same-instance and contention checks, and calls `NetworkServer.Destroy(obj)` even when the requested type does not match. Validate first, claim availability atomically in the authoritative execution path, apply exactly one inventory grant and then despawn; do not yield between claim and commit. Duplicate/retry or rejected requests must not delete another object or grant rewards.
- `Examples/Room/Scripts/Spawner.cs::InitializePool/SpawnHandler/UnspawnHandler/RecycleReward/ClearPool` shows custom handlers and delayed respawn. Host shares server objects instead of creating them via a client spawn handler, but **this revision's `Core/NetworkServer.cs::UnSpawnInternal` explicitly invokes the registered client unspawn handler on Host**. Older documentation saying neither handler runs is insufficient. Trace the installed call chain and provide exactly-once pool return for Host, server-only and remote clients; an extra manual Host return can double-enqueue. Add reset policy, delayed-task cancellation and deregistration; no continuation may spawn after shutdown.
- `Core/NetworkIdentity.cs::ResetState` deliberately retains SyncObjects for same-entity unspawn/respawn. A pool allocation for a **new** logical entity needs explicit inventory/health/availability/owner/timer/visual/buffer reset before spawn. A continuing player may instead retain approved equipment and progression. Test each lifecycle independently; do not clear all state unconditionally.

## Authority and Advanced Sync

- `Examples/AssignAuthority/Scripts/OwnerBehaviour.cs::OnStartAuthority/OnStopAuthority/OnStartClient/OnValidate` illustrates ownership callbacks and `SyncMode.Owner`. Direction, recipient filtering, business authorization and primary-player association are separate contracts; use [mirror-contracts.md](mirror-contracts.md). Revocation stops future permissions/data but cannot erase a secret already received by the old owner.
- `Examples/SyncDirection/Player.cs` intentionally allows client-edited health/collections and warns it is unsafe. Never infer server approval from component direction.
- There is **no `Examples/Prediction` directory** in this revision. Use `Examples/BilliardsPredicted/Player/PlayerPredicted.cs::OnDraggedBall/CmdApplyForce/IsValidMove`, `Examples/StackedPrediction/NetworkManagerStackedPrediction.cs`, and `Examples/BenchmarkPrediction/NetworkManagerPredictionBenchmark.cs` for physics prediction; `Examples/TanksHybrid/Scripts/Tank.cs::CmdFire` and its prefab for Hybrid; `Examples/LagCompensation/{ClientCube,ServerCube}.cs` for historical queries. Select only the relevant technique. Billiards avoids a second Host force application, but `IsValidMove` returns true. Implement real validation.
- Benchmark settings such as StackedPrediction's global solver iterations and disabled vSync are not game defaults. Local lag-compensation/latency demonstrations are mechanism tests, not independent-process transport evidence. Measure correction error, bandwidth, CPU and gameplay feel at the target load before adopting Prediction, Hybrid or lag compensation.
